# 06. API

Соглашения для REST API и WebSocket. Конкретные эндпоинты описываются в коде декораторами Swagger (`@nestjs/swagger`), документация доступна по `/api/docs` (только в разработке и для администратора).

## 1. Общее
- **API-1** (Э0). Базовый путь `/api/v1`. JSON, UTF-8. Имена полей в `camelCase`.
- **API-2** (Э0). Ресурсы во множественном числе: `/clients`, `/orders`, `/orders/:id/items`, `/orders/:id/stage`.
- **API-3** (Э0). Методы: `GET` — чтение, `POST` — создание и действия (`POST /orders/:id/stage`, `POST /orders/:id/approve-estimate`), `PATCH` — частичное изменение, `DELETE` — мягкое удаление или архивирование.
- **API-4** (Э0). Схемы запросов и ответов — Zod в `packages/shared`, из них же генерируются типы для интерфейса. Интерфейс не дублирует типы вручную.
- **API-5** (Э0). Даты — ISO 8601 в UTC (`2026-10-13T09:30:00Z`). Деньги — целое число копеек с суффиксом `Kop` (`totalKop`). Количество — строка с десятичной точкой (`"1.500"`), чтобы не терять точность.

## 2. Авторизация
- **API-10** (Э0). `POST /auth/login` (email, пароль) → access-токен в теле, refresh-токен в httpOnly cookie. `POST /auth/refresh` → новый access, новый refresh (ротация). `POST /auth/logout` → отзыв refresh.
- **API-11** (Э0). Access-токен передаётся в заголовке `Authorization: Bearer <token>`. В токене: `userId`, `companyId`, роли. Права проверяются по актуальным данным из БД (кеш в Redis на 1 минуту), чтобы изменение прав действовало сразу.
- **API-12** (Э0). `GET /auth/me` — текущий пользователь, роли, итоговый список прав, настройки компании.
- **API-13** (Э1). Сброс пароля: администратор задаёт временный пароль, при входе пользователь обязан его сменить. Самостоятельное восстановление по почте — Э2.
- **API-14** (Э3). Интеграционные ключи (`X-Api-Key`) для 1С и сайта — отдельная сущность с ограниченным набором прав.

## 3. Списки
- **API-20** (Э0). Пагинация курсором или страницами: `?page=1&pageSize=50` (максимум 200). Ответ: `{ items: [...], total, page, pageSize }`.
- **API-21** (Э0). Сортировка: `?sort=createdAt:desc,number:asc`.
- **API-22** (Э0). Фильтры: `?stageId=...&managerId=...&createdFrom=2026-10-01&createdTo=2026-10-31&q=поиск`.
- **API-23** (Э0). Включение связанных данных по запросу: `?include=client,assignees`.

## 4. Ошибки
- **API-30** (Э0). Единый формат:
```json
{
  "error": {
    "code": "STAGE_TRANSITION_BLOCKED",
    "message": "Нельзя перевести заказ в «Готов к выдаче»: не заполнен протокол испытаний",
    "details": [{ "field": "testResults", "reason": "required" }],
    "requestId": "01J…"
  }
}
```
- **API-31** (Э0). Коды HTTP: 400 — ошибка валидации (`VALIDATION_ERROR` + поля), 401 — не авторизован, 403 — нет прав (`FORBIDDEN`), 404 — не найдено, 409 — конфликт (`CONFLICT`: дубль, устаревшая версия, недостаточно на складе), 422 — нарушение бизнес-правила (`STAGE_TRANSITION_BLOCKED`, `DISCOUNT_APPROVAL_REQUIRED`, ...), 429 — лимит запросов, 500 — внутренняя ошибка.
- **API-32** (Э0). Сообщения об ошибках — на русском, пригодны для показа пользователю. Коды ошибок перечислены в `packages/shared/errors.ts`.

## 5. Конкурентное изменение
- **API-40** (Э1). У изменяемых сущностей (заказ, клиент, позиции сметы) есть поле `version`. `PATCH` передаёт текущую `version`; если запись изменили с тех пор — ответ 409, интерфейс предлагает обновить данные.

## 6. Файлы
- **API-50** (Э1). Загрузка: `POST /files/upload-url` (имя, тип, размер) → подписанный URL S3 и `fileId`; клиент загружает файл напрямую в S3; `POST /files/:id/complete` подтверждает загрузку (сервер проверяет размер и тип, создаёт превью для изображений).
- **API-51** (Э1). Скачивание: `GET /files/:id` → редирект на временную подписанную ссылку.

## 7. WebSocket (Socket.IO)
- **API-60** (Э1). Подключение к `/ws` с access-токеном. Сервер подписывает сокет на комнаты: `user:<id>`, `company:<id>`, а клиент сам подписывается на `order:<id>` при открытии заказа и `chat:<channelId>` для каналов чата.
- **API-61** (Э1). События сервер → клиент:

| Событие | Комната | Данные |
|---|---|---|
| `order.updated` | `company`, `order:<id>` | id, изменённые поля, version |
| `order.stageChanged` | `company`, `order:<id>` | id, fromStageId, toStageId, by |
| `comment.created` / `comment.updated` | `order:<id>` | комментарий |
| `chat.message` / `chat.messageUpdated` | `chat:<id>` | сообщение |
| `chat.typing` | `chat:<id>` | userId |
| `notification.new` | `user:<id>` | уведомление |
| `lead.created` / `lead.updated` | `company` | заявка (с учётом прав) |
| `clientMessage.new` | `company`, `order:<id>` | сообщение клиента (Э4) |
| `call.incoming` | `user:<id>` | номер, найденный клиент (Э4) |

- **API-62** (Э1). WebSocket только оповещает. Изменения данных всегда идут через REST, чтобы права и валидация работали в одном месте. Отправка сообщения в чат — тоже `POST /chat/channels/:id/messages`.
- **API-63** (Э1). События фильтруются по правам получателя: мастер не получает `order.updated` с полями маржи, менеджер (при включённой настройке) — события по чужим заказам.
- **API-64** (Э1). После переподключения клиент перезапрашивает открытые данные (TanStack Query invalidate), чтобы не потерять события за время обрыва.

| `POST /webhooks/avito/:secret` | Авито | Секрет | Э4 |

## 9. Версионирование
- **API-70** (Э0). Несовместимые изменения API вводятся в новой версии (`/api/v2`) только для внешних потребителей (1С, сайт). Собственный интерфейс CRM выкладывается вместе с API и всегда совместим.
