## Страница кейса

### Задача
Сервисная компания ремонтирует и собирает промышленные гидростанции. Заявки приходят по телефону, почте и в мессенджеры, обсуждения заказов разбросаны по чатам, руководитель не видит, какой заказ на каком этапе и где он застрял. Нужна система, которая ведёт заказ от первого звонка до выдачи и не даёт пропустить важные шаги — например, начать ремонт без согласованной с клиентом сметы.

### Решение
CRM под процессы именно этого бизнеса, а не универсальная «карточка сделки»:
- **Четыре воронки** — ремонт в цеху, выездной ремонт, сборка под заказ и сборка типовых станций, у каждой свои этапы и нормы времени.
- **Проверки этапов**: система не пропустит заказ дальше, если не хватает фото при приёмке, согласованной сметы или мастера. Руководитель может сделать исключение только с комментарием — оно остаётся в журнале.
- **Смета с согласованием**: мастер предлагает работы и запчасти без цен, менеджер ставит цены и фиксирует согласие клиента; любые изменения после согласования помечаются как доп. работы.
- **Роли**: руководитель, менеджер, мастер, бухгалтер. Мастер видит только свои заказы и не видит цен — эти данные вообще не уходят с сервера.
- **Общение внутри заказа**: лента с фото и @упоминаниями, чат команды и уведомления вместо разрозненных мессенджеров. Изменения коллег видны сразу, без перезагрузки.
- **Выезды**: календарь мастеров с перетаскиванием и предупреждением о пересечениях, экран мастера на объекте с большими кнопками, который работает даже без связи.
- **Дашборд руководителя**: заказы без движения дольше нормы, просрочки, выручка и маржа за месяц.

### Как сделано
- Сервер на **NestJS + PostgreSQL**, интерфейс на **React + TypeScript**, живые обновления через **WebSocket**, мобильная версия устанавливается как приложение (**PWA**).
- Правила этапов, права ролей и расчёт сметы вынесены в общий модуль и покрыты тестами — сервер и интерфейс проверяют данные одинаково.
- Данные компаний изолированы на уровне базы — систему можно продавать нескольким компаниям без переделки.
- Перед публикацией — аудит интерфейса и проверка безопасности: ограничение попыток входа, защитные заголовки, проверка типа загружаемых файлов, изоляция данных.
- Начинали с идеи и технического задания: роли, процессы, модель данных, план этапов.

## Что нужно для публикации приложения
1. Репозиторий на GitHub (публичный — для бесплатного GitHub Pages).
2. Settings → Pages → Source: **GitHub Actions**.
3. По желанию: Settings → Secrets and variables → Actions → Variables:
   - `AUTHOR_NAME` — ваше имя для подписи «Разработка — …»;
   - `AUTHOR_URL` — адрес вашего сайта-портфолио (`https://…`) для кнопки «Обсудить похожий проект».
4. Push в ветку `main` — приложение соберётся и опубликуется само по адресу `https://<логин>.github.io/<репозиторий>/`.
